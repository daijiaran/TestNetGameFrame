# MyNetGameProject 网络层与业务层解耦解决方案

> 输出日期: 2026-05-02
> 依据文档: `网络层与业务层耦合分析报告.md`

---

## 1. 目标

把当前“网络层负责收包 + 管数据 + 调业务 + 广播”的结构，拆成下面四层职责：

- 传输层: 只负责 `Socket` 收发
- 协议层: 只负责包解析、包序列化、路由
- 应用层: 只负责“收到某个命令后要做什么”
- 领域层: 只负责玩家、场景物体、战斗等业务状态

最终目标不是“完全重写”，而是先把最危险的直接耦合拆开：

- `ServiceUpdate` 不再直接操作玩家业务
- `ServiceUpdate` 不再持有 `PlayersData` / `ScenesObjectData`
- `Server` 不再每帧把业务字典倒灌回网络层
- `NetConect` 不再向上层直接暴露 `UserJoinPacket`、`ScenesItemDataPacket` 这类网络包细节

---

## 2. 先看当前代码里的真实问题

结合当前实现，耦合点主要有 4 个：

### 2.1 服务端网络层仍然拥有业务数据

文件: `Assets/Scripts/Server/ServiceUpdate.cs`

- `playersData`
- `ScenesObjectData`

这会导致 `ServiceUpdate` 同时承担：

- 客户端地址管理
- 玩家同步数据存储
- 场景同步数据存储
- 收包解析
- 业务转发
- 广播发送

这是本次最优先拆掉的点。

### 2.2 服务端只是“伪注入”，核心依赖还没真正分层

文件: `Assets/Scripts/Server/Server.cs`

虽然已经有：

- `IPlayerManager`
- `ISceneObjectManager`
- `INetworkService`

但 `Server.Update()` 里仍然在做：

```csharp
serviceUpdate.playersData.Players = serverAllPlayerManager.AllPlayerInstancesUserPositionPackets;
serviceUpdate.ScenesObjectData.ScenesItem = serverAllitemManager.AllItemsTransData;
serviceUpdate.Update();
serviceUpdate.SendToAllPlayer();
```

这说明网络层仍依赖业务层内部结构，只是换了一个地方耦合。

### 2.3 收包后直接调用业务方法

文件: `Assets/Scripts/Server/ServiceUpdate.cs`

`ParsePacket()` 里直接：

- `NewPlayerJoin(...)`
- `OnUserMove(...)`
- `UserAttackData(...)`

这使得新增协议时必须修改网络层核心类，违反开闭原则。

### 2.4 客户端网络层把“网络包”直接暴露给业务/UI

文件: `Assets/Scripts/Client/NetConect.cs`

当前直接暴露：

- `Action<UserJoinPacket> netUserJoinEvent`
- `Action<string, UserPositionAndStatusPacket> takePlayerPacket`
- `Action<ScenesItemDataPacket> takeSceneItemPacket`

这会让客户端业务层依赖网络协议对象，后面协议一改，业务层也跟着改。

---

## 3. 建议采用的目标结构

### 3.1 服务端

```text
UdpTransport
  -> ServerPacketRouter
    -> IServerCommandHandler
      -> ServerAllPlayerManager / ServerAllitemManager / CombatService
```

职责划分：

- `UdpTransport`: 收发原始字节
- `ServerPacketRouter`: 根据 `PacketType` 解析并路由
- `IServerCommandHandler`: 应用层命令入口
- `ServerAllPlayerManager`: 玩家状态管理
- `ServerAllitemManager`: 场景物体状态管理
- `ServerStateSyncService`: 统一组织“当前世界状态广播”

### 3.2 客户端

```text
UdpTransport
  -> ClientPacketRouter
    -> IClientMessageHandler
      -> NetworkPlayerManager / NetworkScensItemManager / UI
```

职责划分：

- `NetConect` 后续只做传输和入队
- `ClientPacketRouter` 负责协议解析
- `IClientMessageHandler` 接收“语义化消息”而不是原始网络包

---

## 4. 核心解决方案

## 4.1 服务端引入命令处理接口，切断 `ServiceUpdate -> PlayerManager`

新增接口：

```csharp
public interface IServerCommandHandler
{
    void HandleJoin(string clientKey, EndPoint remoteClient, UserJoinPacket packet);
    void HandleMove(string clientKey, UserMovePacket packet);
    void HandleAttack(string clientKey, EndPoint remoteClient, UserAttackPacket packet);
}
```

然后把 `ServiceUpdate` 的依赖从 `IPlayerManager` 改成 `IServerCommandHandler`。

这样变化是：

- 现在: `ServiceUpdate -> IPlayerManager`
- 改后: `ServiceUpdate -> IServerCommandHandler`

好处：

- 网络层不再知道“玩家管理器”是谁
- 后面加入聊天、技能、拾取物品时，只扩展 handler，不继续污染 `ServiceUpdate`

---

## 4.2 把状态广播从 `ServiceUpdate` 中拆出去

建议新建：

```csharp
public interface IWorldStateProvider
{
    IEnumerable<UserPositionAndStatusPacket> GetPlayerStates();
    IEnumerable<ScenesItemDataPacket> GetSceneStates();
    IReadOnlyDictionary<string, EndPoint> GetClientEndpoints();
}
```

再新建：

```csharp
public class ServerStateSyncService
{
    private readonly INetworkService networkService;
    private readonly IWorldStateProvider worldStateProvider;

    public void BroadcastSnapshot() { ... }
}
```

这样以后：

- `ServiceUpdate` 只管“怎么发”
- `ServerStateSyncService` 决定“发什么”
- `ServerAllPlayerManager` / `ServerAllitemManager` 决定“状态从哪里来”

要点：

- 删除 `ServiceUpdate.playersData`
- 删除 `ServiceUpdate.ScenesObjectData`
- 删除 `Server.Update()` 中把字典塞回 `serviceUpdate` 的代码

---

## 4.3 地址簿单独抽成 `ClientRegistry`

当前 `playersData.ClientEndPoints` 混在网络类里，不利于职责清晰。

建议新建：

```csharp
public interface IClientRegistry
{
    void Upsert(string clientKey, EndPoint remoteClient);
    bool TryGet(string clientKey, out EndPoint endPoint);
    IReadOnlyDictionary<string, EndPoint> GetAll();
    void Remove(string clientKey);
}
```

好处：

- 客户端地址管理独立
- 断线清理逻辑集中
- 广播目标来源稳定

---

## 4.4 客户端不要再把协议包直接往上抛

把 `NetConect` 当前这些事件：

- `Action<UserJoinPacket>`
- `Action<string, UserPositionAndStatusPacket>`
- `Action<ScenesItemDataPacket>`

替换成更高层的消息接口，例如：

```csharp
public interface IClientMessageHandler
{
    void OnPlayerJoined(PlayerJoinedMessage message);
    void OnPlayerStateUpdated(PlayerStateMessage message);
    void OnSceneItemUpdated(SceneItemMessage message);
}
```

其中 `PlayerJoinedMessage` / `PlayerStateMessage` / `SceneItemMessage` 是客户端应用层 DTO，不直接复用网络包类。

这样：

- 网络协议变了，客户端业务层不一定跟着变
- UI/表现层不需要知道二进制包结构

---

## 4.5 把“协议对象”和“业务对象”分开

当前很多地方直接改包对象字段，例如 `ServerAllPlayerManager.UpdatePlayerData()` 直接改 `UserPositionAndStatusPacket`。

建议改成：

- 领域层维护 `PlayerState`
- 发送前由 `PlayerState -> UserPositionAndStatusPacket`

即：

```text
PlayerInstance / PlayerState
  -> PlayerStateSnapshot
    -> PacketAssembler
      -> UserPositionAndStatusPacket
```

好处：

- 网络包不再承担“内存中的实时业务状态”
- 包对象变成短生命周期传输对象
- 后面换协议格式更容易

---

## 5. 推荐重构顺序

## 阶段 1: 低风险拆耦

目标: 不改玩法，只改依赖方向

步骤：

1. 新增 `IServerCommandHandler`
2. `ServiceUpdate.Initialize()` 改为注入 `IServerCommandHandler`
3. `Server` 实现一个 `ServerCommandHandler`
4. `ServiceUpdate.ParsePacket()` 只负责解析后转交 handler
5. 保留现有 `SendToAllPlayer()` 逻辑，先不动广播实现

这一步完成后，最关键的“网络层直调业务层”就先切断了。

## 阶段 2: 拆状态同步

目标: 去掉 `ServiceUpdate` 中的业务数据

步骤：

1. 引入 `IClientRegistry`
2. 引入 `IWorldStateProvider`
3. 新建 `ServerStateSyncService`
4. `Server.Update()` 改为：

```csharp
serviceUpdate.Update();
stateSyncService.BroadcastSnapshot();
```

5. 删除：

- `ServiceUpdate.playersData`
- `ServiceUpdate.ScenesObjectData`
- `UpdatePlayerData(...)`
- `UserPositionPacketProcess(...)`

这一步完成后，`ServiceUpdate` 会变成真正的网络服务。

## 阶段 3: 客户端消息语义化

目标: 去掉 `NetConect` 对上层的协议泄漏

步骤：

1. 新增 `ClientPacketRouter`
2. 新增 `IClientMessageHandler`
3. `NetConect` 解析后不直接触发 `Action<Packet>`
4. 改由 router 输出客户端消息对象
5. `NetworkPlayerManager` / `NetworkScensItemManager` 只处理消息 DTO

## 阶段 4: 协议与状态彻底分离

目标: 网络包只做传输

步骤：

1. 领域层维护 `PlayerState` / `SceneItemState`
2. 新增 assembler / mapper
3. 广播前临时生成 packet
4. 不再长期缓存 `UserPositionAndStatusPacket`

---

## 6. 推荐类设计

### 6.1 服务端入口编排

建议把 `Server` 调整为组装器，而不是业务承担者：

```csharp
Server
  - ServiceUpdate transport
  - ClientRegistry clientRegistry
  - ServerCommandHandler commandHandler
  - ServerStateSyncService stateSyncService
  - ServerAllPlayerManager playerManager
  - ServerAllitemManager sceneItemManager
```

`Server` 只负责：

- 创建实例
- 注入依赖
- 驱动 Update

不再负责手动搬运字典。

### 6.2 命令处理器

建议新增 `ServerCommandHandler.cs`：

```csharp
public class ServerCommandHandler : IServerCommandHandler
{
    private readonly IClientRegistry clientRegistry;
    private readonly IPlayerManager playerManager;

    public void HandleJoin(...) { ... }
    public void HandleMove(...) { ... }
    public void HandleAttack(...) { ... }
}
```

这样 `ServerAllPlayerManager` 可以继续只做玩家管理，不必顺带承担网络入口职责。

---

## 7. 针对你当前项目的最小落地方案

如果你想先用最小代价见效，我建议先做这 5 个改动：

1. 把 `ServiceUpdate` 里的 `IPlayerManager` 依赖改成 `IServerCommandHandler`
2. 把加入、移动、攻击三个分支的处理迁到 `ServerCommandHandler`
3. 新建 `ClientRegistry`，让 `clientKey -> EndPoint` 从 `PlayersData` 里独立出来
4. 把 `Server.Update()` 中对 `serviceUpdate.playersData` / `ScenesObjectData` 的赋值删掉
5. 新建 `ServerStateSyncService` 接管 `SendToAllPlayer()`

这 5 步做完后，架构会从“高耦合”降到“中等可维护”，而且不会一下子把整个项目打散。

---

## 8. 风险与注意事项

### 8.1 不建议一步到位全量重写

原因：

- 当前项目还有单例、Shared 混合客户端/服务端逻辑等其他耦合点
- 如果一口气一起改，排查问题会非常困难

### 8.2 先保协议兼容，再重构内部

建议先保持这些包不变：

- `UserJoinPacket`
- `UserMovePacket`
- `UserAttackPacket`
- `UserPositionAndStatusPacket`
- `ScenesItemDataPacket`

先重构调用关系，再重构协议模型。

### 8.3 广播逻辑要留意重复发送

当前 `Server.Update()` 已经每帧调用：

- `serviceUpdate.Update()`
- `serviceUpdate.SendToAllPlayer()`

拆分时要避免：

- 收包线程触发一次广播
- Update 再触发一次广播

建议统一由 `ServerStateSyncService` 在主线程单点驱动。

---

## 9. 结论

这份报告对应的正确解决方向，不是继续给 `ServiceUpdate` 增加更多接口，而是把它真正缩回“网络传输 + 包路由”。

这次重构最关键的 3 个动作是：

1. 用 `IServerCommandHandler` 切断网络层直调业务
2. 用 `ServerStateSyncService` 把状态广播从 `ServiceUpdate` 拆出去
3. 用客户端消息 DTO 切断 `NetConect` 对上层的协议泄漏

如果这三步完成，这个项目的网络层和业务层就会从“互相缠住”变成“通过接口协作”，后面再处理单例、Shared 混用、事件分散这些问题会顺很多。
